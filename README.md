# Сервис моделирования трассировки тепловых сетей для технологического присоединения новых зданий

**Демо:** [теплогис.рф](https://теплогис.рф)

Сервис по загруженному GeoJSON сам строит и проверяет трассы подключения
объектов капитального строительства (ОКС) к существующей тепловой сети:
учитывает пространственные ограничения территории, считает стоимость и
возвращает до трёх ранжированных вариантов. Результат — не эскиз, а
самостоятельно проверенный GeoJSON: сервис явно доказывает отсутствие более
дешёвого маршрута там, где поиск способен это доказать, а не просто
останавливается по таймеру.

Помимо обязательной двумерной трассировки реализован необязательный режим с
учётом глубины заложения (глубина, уклон, вертикальные зазоры спецпереходов) —
отдельный расчёт со своим набором вариантов.

Встроенный веб-интерфейс (`/`) закрывает весь сценарий: загрузка GeoJSON,
расчёт (2D и с учётом глубины, все ОКС или выбранные по номерам, до трёх
вариантов, необязательная строгая проверка полноты поиска), интерактивная
карта результата и выгрузка готового GeoJSON. Отдельный клиент не нужен.

## Алгоритм

Расчёт идёт по шагам, каждый — со своим контрактом и API (`docs/*-api.md`):

1. **Импорт и геометрия.** GeoJSON читается потоково (валидатор проверяет
   схему токен за токеном, не строя дерево всего файла), переносится в
   PostGIS с перепроецированием WGS84 → EPSG:32637 (UTM) и индексируется.
2. **Пространственные ограничения.** Табличные правила приложения (отступы,
   углы и коэффициенты спецперехода для ОКС, парков, дорог, трамвайных путей,
   газопровода, силового кабеля, существующей сети) реализованы дважды —
   как PostGIS-функции (эталон) и как их построчно сверенный JTS-эквивалент
   в памяти для горячего пути поиска, — что подтверждается перекрёстными
   тестами одного и другого движка на реальных импортах.
3. **Маршрутизация.** Подробно — в разделе [«Алгоритм поиска маршрута»](#алгоритм-поиска-маршрута) ниже.
4. **Сборка сети.** Отдельные маршруты нодируются (попарно разрезаются в
   каждой точке геометрического пересечения — включая пересечения маршрутов
   разных целей — так что общий узел получается по построению, а не
   проверкой постфактум), после чего по ним назначаются условный диаметр
   (расход и предельная длина по таблице 1, диаметр не убывает к точке
   присоединения) и место присоединения к существующей сети (переиспользование
   камеры в пределах 10 м с учётом лимита в четыре примыкания либо новая
   камера).
5. **Стоимость и ранжирование.** Стоимость участков, камер и врезок считается
   по таблицам приложения; неподключённые точки штрафуются; варианты
   дедуплицируются по существенному отличию трассы и ранжируются по формуле
   `S = 0,7·(C / 25 000 000) + 0,3·(L / 100)`.
6. **Экспорт.** Каждый вариант строится и полностью самопроверяется (контракт
   выходных данных + техническое приложение, включая повторную пространственную
   проверку каждой линии) по одному варианту за раз и сразу пишется в файл
   потоковым `JsonGenerator` — ни один вариант результата (до 500 МБ по
   приложению) не держится в памяти дважды.

Итоговый контракт выходных данных, коды ошибок и подробности каждого шага —
в `docs/*-api.md`, `docs/input-contract.md`, `docs/web-ui.md` и `docs/operations.md`.

### Алгоритм поиска маршрута

Маршрут для каждой точки подключения ищется отдельно, поиском A\* по графу
соседства, построенному заранее для всего импорта.

**Граф.** Узлы — это сама точка подключения, точки примыкания к существующей
сети (кандидаты присоединения в радиусе выборки) и узлы навигационной сетки,
которые ставятся на границах буферизованных пространственных ограничений
(отступ от ОКС, парков, дорог, газопровода и т. д. — раздел 4 приложения).
Рёбра графа — это (а) последовательные вершины одного и того же буферизованного
контура, (б) связи между `k` ближайшими соседями по всему множеству узлов,
построенные через равномерную сетку за время, близкое к линейному, а не
полным перебором пар, и (в) прямые связи от целевой точки к точкам выхода
из её собственного полигона ОКС — чтобы финальный подход к цели не терялся
среди плотной сетки узлов на границе того же полигона.

**Проверка ребра.** Каждое ребро графа проверяется на допустимость движком
пространственных ограничений (см. выше): нарушение отступа, слишком острый
угол пересечения специального перехода или пересечение непроходимого
препятствия делает ребро недопустимым для поиска. Допустимые рёбра взвешены
не длиной напрямую, а длиной с коэффициентом `Kспец` каждого участка
специального перехода — поиск минимизирует именно то, что потом считает
формула стоимости, а не просто кратчайший путь по метру.

**Ограничение поворота.** На каждом шаге поиска угол между входящим и
исходящим отрезком пути проверяется отдельно и не должен превышать 90°
(раздел 2.1 приложения) — недопустимые повороты в граф поиска не попадают
вовсе, а не отбрасываются постфактум.

**Упрощение и проверка на «крюк».** Найденный путь после этого пытается
срезать промежуточные вершины напрямую там, где прямой отрезок между двумя
несмежными точками пути сам по себе допустим — это убирает лишние мелкие
изломы, оставшиеся от дискретности навигационной сетки. Итоговая длина пути
сверяется с расстоянием по прямой до ближайшей точки присоединения: путь
длиннее его в 1,5 раза плюс 30 м считается подозрительно длинным крюком —
признак того, что стоит попробовать иной набор точек присоединения, а не
взять первый найденный путь как есть.

**Три уровня эскалации.** Если точка не подключилась на обычном поиске
(`k`=24 соседа, до 8 000 узлов сетки, до 400 точек примыкания), для всех
ещё нерешённых точек одного профиля (не более 10 на профиль) поиск
повторяется в «широком» режиме с более богатым графом (`k`=64, до 30 000
узлов, до 1 200 точек примыкания, бюджет 40 000 состояний поиска). Если и
после этого остаются нерешённые точки (не более 4 на профиль — это уже
самые сложные случаи), для них запускается «сверхширокий» поиск: вдвое
плотнее граф широкого поиска и втрое больше бюджет состояний. Каждый
следующий уровень запускается только для точек, которые предыдущий не
разрешил ни в одну, ни в другую сторону, — не пересчитывает то, что уже
решено.

**Доказательство отсутствия маршрута.** Если точка не подключилась даже на
сверхширoком уровне, сервис не просто сообщает «не найдено» — он запускает
заливку свободного пространства (flood fill по сетке с шагом 1 м) от точки
во все стороны. Если залитая область гаснет, не дотянувшись до сети, раньше
8 000 клеток, это формальное доказательство, что точка со всех сторон
заперта ограничениями и маршрута для неё не существует в принципе — не
только тот, что поиск не смог найти. Если же заливка обрывается по лимиту,
не исчерпав пространство, сервис честно помечает точку как
«не проверено» (`SEARCH_INCOMPLETE`), а не выдаёт это за доказанное
отсутствие маршрута.

Профилей поиска — три (по числу возможных вариантов результата): они
предпочитают разные существующие сети/точки присоединения в качестве
кандидата, поэтому дают содержательно разные трассы, а не косметические
вариации одной и той же.

## Технологии и зависимости

**Бэкенд** — Java 11, Spring Boot 2.6.3, Maven.

| Библиотека | Версия | Назначение |
| --- | --- | --- |
| spring-boot-starter-web/jdbc/actuator | 2.6.3 | HTTP API, JDBC, health-проверки |
| org.locationtech.jts:jts-core | 1.19.0 | Геометрический движок (JTS) |
| org.flywaydb:flyway-core | (BOM) | Миграции схемы БД |
| org.postgresql:postgresql | (BOM) | JDBC-драйвер PostgreSQL |
| org.springdoc:springdoc-openapi-ui | 1.7.0 | Swagger UI / OpenAPI |
| com.fasterxml.jackson (BOM) | 2.17.3 | JSON |
| org.testcontainers (test) | 1.21.4 | Интеграционные тесты с настоящим PostGIS |

**Хранилище** — PostgreSQL 14 + PostGIS 3.4 (см. `docker-compose.yml`).

**Фронтенд** — статические `HTML/CSS/JS` без фреймворка и без отдельной
сборки (`backend/src/main/resources/static`), отдаются тем же Spring Boot
приложением.

**Инфраструктура запуска** — Docker и Docker Compose 1.29.2 (поддерживается
и `docker compose`).

## Быстрый старт

```sh
git clone https://github.com/ZolotorevOleg/teplogis
cd teplogis
docker-compose up -d --build
```

Поднимутся два контейнера — PostgreSQL/PostGIS и сам сервис. Первый запуск
собирает образ бэкенда и может занять несколько минут.

После старта:

- Веб-интерфейс: http://localhost:8080/
- Swagger UI: http://localhost:8080/swagger-ui/index.html
- OpenAPI: http://localhost:8080/v3/api-docs
- Готовность сервиса и БД: http://localhost:8080/actuator/health

Проверка через API вместо интерфейса:

```sh
curl -f -F "file=@Датасет скорректированный.geojson" http://localhost:8080/api/v1/imports
curl http://localhost:8080/api/v1/imports/UUID
curl -X POST http://localhost:8080/api/v1/imports/UUID/geometry
curl -H "Content-Type: application/json" -d '{"maxVariants":3}' \
  -o result.geojson http://localhost:8080/api/v1/imports/UUID/outputs/geojson
curl -H "Content-Type: application/geo+json" --data-binary @result.geojson \
  http://localhost:8080/api/v1/imports/UUID/outputs/validate
```

Полный список эндпоинтов — в `docs/*-api.md` и в Swagger UI. В PowerShell
используйте `curl.exe` (не алиас `Invoke-WebRequest`).

Успешная загрузка возвращает `201`, UUID, `READY`, число объектов и байт,
заголовок `Location`; это не означает, что маршрут уже построен. `422` —
ошибка содержимого с JSON-путём до проблемы, `413` — превышение размера,
`429` — заняты оба слота одновременной HTTP-загрузки, `503` — ошибка
хранилища, `404` — неизвестный UUID.

Первый расчёт по всем ОКС может занимать несколько минут на большом импорте;
повторный запрос с теми же параметрами возвращается сразу из кэша.

### Остановка и повторный запуск

```sh
docker-compose down          # остановка контейнеров, данные (volumes) сохраняются
docker-compose down -v       # то же, но с удалением volumes (данные теряются)
docker-compose up -d         # запуск конейнеров без пересборки образа
```

## Тесты

Локально (нужны Java 11 и Maven 3.9, Docker — для интеграционных тестов):

```sh
mvn -f backend/pom.xml clean package     # только unit-тесты
mvn -f backend/pom.xml -Punit test       # явно только unit-тесты
mvn -f backend/pom.xml verify            # + интеграционные тесты (Testcontainers + настоящий PostGIS)
docker-compose config                    # проверка docker-compose.yml
```

Интеграционные тесты запускают реальный PostGIS через Testcontainers и не
заменяются H2/моками. На Windows без системной Java 11 можно использовать
`powershell -File scripts/check.ps1` (опции `-Memory`, `-Integration`) —
скрипт скачивает инструменты в `work/tools`, не трогая системную Java.

## Конфигурация

Все переменные необязательны и имеют рабочие значения по умолчанию для
локального запуска через `docker-compose.yml`:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `HTTP_PORT` | `8080` | Локальный порт, на котором публикуется API/интерфейс |
| `DB_PASSWORD` | `heat-local-dev` | Пароль PostgreSQL. **Только для локального запуска** — см. ниже |
| `BACKEND_MEMORY` | `1g` | Лимит памяти контейнера бэкенда (куча JVM = 75% лимита) |
| `MAX_CONCURRENT_IMPORTS` | `2` | Сколько одновременных multipart-загрузок допускается |
| `DB_POOL_SIZE` | `24` | Размер пула соединений HikariCP |

Пароль `heat-local-dev` — явный, документированный пароль для локальной
разработки, не секрет. Для любого окружения, доступного не только с
локальной машины, скопируйте `.env.example` в `.env` (файл в `.gitignore`,
в репозиторий не попадает) и задайте свой `DB_PASSWORD`, либо передайте
переменную окружения напрямую — никогда не храните реальный пароль в
закоммиченных файлах. Порт базы данных наружу не
публикуется, API слушает `127.0.0.1` по умолчанию.

Расчёт большого импорта (глубокая структура ограничений, до 500 МБ на один
вариант результата) требует поднять `BACKEND_MEMORY`: расчёт района в
несколько тысяч объектов укладывается в значение по умолчанию (1 ГиБ), а
город масштаба сотен тысяч объектов с результатом в сотни мегабайт требует
6–8 ГиБ (`BACKEND_MEMORY=8g docker-compose up -d --build`, без пересборки
образа).

## Структура проекта

- `backend/` — исходники Java (Spring Boot 2.6.3), тесты, Flyway-миграции,
  статический фронтенд в `backend/src/main/resources/static`.
- `docker-compose.yml` — PostgreSQL/PostGIS и сервис, постоянные volumes.
- `.env.example` — шаблон переменных для `docker-compose.yml` (скопировать в `.env`).
- `Датасет скорректированный.geojson` — конкурсный датасет (144 объекта, 17 ОКС) для локальной проверки.
- `docs/` — API по шагам расчёта (`*-api.md`), схема входных данных
  (`input-contract.md`), режим глубины (`depth-mode.md`), веб-интерфейс
  (`web-ui.md`), эксплуатация (`operations.md`), сопроводительная
  документация по требованиям задания (`documentation.md`).
- `scripts/` — вспомогательные скрипты (проверка окружения, нагрузочные и
  дымовые тесты).

## Хранение данных

Оригинал импорта хранится в volume `uploads`, каталог объектов и метаданные —
в PostgreSQL (PostGIS + pgcrypto, миграции Flyway). Загрузка ограничена
3 GiB (3 221 225 472 байт). Файл сначала записывается на диск, затем
валидатор читает его токенами, не строя дерево всего документа в памяти.
Подробности — в `docs/input-contract.md`.
